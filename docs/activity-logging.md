# Quick activity logging and repeating watering

- Small activity forms, including harvest, do not save or recover drafts. Closing discards unfinished values immediately, without a discard prompt. Failed-save retries retain their mutation ID only while the form stays open; saved journal records are unaffected.
- Watering opens with its activity date and Save. An amount can be added optionally; there are no general measurement fields in watering.
- Both watering entry points use a compact optional amount panel with an animated chevron. Its heading opens or closes the editor while retaining the value and showing the amount in the collapsed summary. “Remove amount” clears the value without collapsing. The latest saved amount appears with “Using last amount”; existing entries retain their own values. The latest journal record is authoritative, with a per-account/per-plant device cache for offline use. Failed saves do not update that cache.
- Measurements is a separate editable/searchable journal category for pH, height and soil moisture. At least a reading or an observation is required. Existing health records remain supported.
- Repotting and Flushing are dated, editable journal activities with optional observations. Their general measurement fields stay in Measurements. Both are available in journal search filters.
- Harvesting in Add activity opens the existing harvest flow with the selected date, optional weight/notes and explicit finish-grow confirmation. The same atomic harvest operation records history, ends living growth and clears repeating watering. Pruning stays under Training.
- Repeating watering is optional. The user supplies an interval of 1–365 calendar days, a local time and a positive amount. The plant's time zone is used, with the device time zone as an explicit fallback. Its first repeat is after the selected activity date and the current time; setting up a routine does not create retrospective entries.
- The routine and initial watering save atomically. Existing routines show a compact summary and Stop repeating action, including when the selected day already has a watering entry.
- The foreground coordinator reuses the shared owned-plant subscription. It checks due routines each minute and on app resume, catches up at most 30 occurrences per plant per pass, and retries remaining work later. No background execution is promised by the current UI.
- Both client and cloud paths use the existing deterministic daily watering ID. Existing daily or legacy watering entries are preserved, concurrent commits reconcile, and deleting an occurrence does not regenerate it after the routine advances. Generated entries show “Automatically recorded”, retain their scheduled time and record their actual creation time separately.
- Inactive, harvested, drying, curing, completed and deleting plants receive no new automatic watering. Stopping a routine prevents future entries. Restoring a backup copies the history with routines disabled, preventing duplicate automation.
- The optional `recordRepeatingWatering` cloud function runs every 15 minutes when deployed. It supports closed-app execution and the same transaction/deduplication contract. It has not been deployed by this change; no billing plan was changed. Current functionality uses foreground logging and catch-up on reopening.

Validation includes unit tests, both TypeScript builds, lint/architecture checks and disposable Firebase emulator scenarios for actual owner-rule saves, concurrent catch-up, stopping, invalid settings, manual-entry preservation and ended-cycle behavior. No production plant records were created for tests.
